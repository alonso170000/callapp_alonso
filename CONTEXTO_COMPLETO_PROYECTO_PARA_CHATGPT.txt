1. RESUMEN DEL PRODUCTO
-----------------------

CallerApp HADA es un CRM inmobiliario móvil para agentes de ventas. Permite iniciar sesión,
consultar prospectos, registrar llamadas y seguimientos, capturar discovery, administrar la
agenda, recibir recordatorios y manejar preferencias del perfil.

El sistema está formado por dos proyectos que se comunican mediante una API REST:

- CallerApp/: aplicación Flutter para Android.
- CRM-hada/: backend Node.js/Express conectado a MySQL.

La aplicación tiene enfoque offline-first. Las lecturas usan una instantánea local cuando la
red no está disponible y las escrituras compatibles se proyectan inmediatamente en SQLite,
se guardan en una outbox y se sincronizan al recuperar conectividad. MySQL, accedido por la
API, continúa siendo la fuente de verdad remota.

5. ARRANQUE, SESIÓN Y NAVEGACIÓN
--------------------------------

Al arrancar:

1. AuthService intenta restaurar la sesión desde flutter_secure_storage.
2. Si el JWT guardado ya expiró, se elimina la sesión local.
3. NotificationService inicializa las notificaciones locales.
4. OutboxService inicia su procesamiento sin bloquear el primer render.
5. LocalMaintenanceService ejecuta el mantenimiento si corresponde.
6. MaterialApp.router usa es-MX y escucha AppearanceController.

Rutas actuales:

- /login: inicio de sesión.
- /home: shell autenticado principal.
- /prospectos/:phone: detalle de prospecto.

El router inicia en /login. Si no hay sesión redirige cualquier ruta protegida hacia /login;
si ya hay sesión y se abre /login, redirige a /home.

/home contiene un IndexedStack con cuatro pestañas que conservan su estado:

1. Inicio.
2. Prospectos.
3. Agenda.
4. Perfil.

Las cuatro pestañas no son rutas independientes. La navegación principal usa go_router; no
se debe introducir Navigator para rutas de aplicación.

La ruta de detalle recibe preferentemente un ProspectRecord o ProspectDetailArguments por
state.extra. El fallback por teléfono todavía consulta demoProspects, por lo que un deep link
sin extra puede no representar todos los datos remotos actuales.


6. AUTENTICACIÓN Y MULTIÁMBITO
------------------------------

AuthService envía POST /api/v1/auth/login con username y password. El login requiere una
respuesta válida con status success y token JWT. La URL base se configura en compilación:

  flutter run --dart-define=API_BASE_URL=https://servidor.example.com

Existe una URL de Render predeterminada en el código, pero debe verificarse antes de afirmar
que el despliegue está disponible. El valor debe ser una URL HTTPS base, sin /api/v1.

La sesión conserva token, id, nombre, correo, teléfono y desarrollo activo. El almacenamiento
seguro permite restaurarla después de reiniciar la app. La expiración local se comprueba con
el claim exp; un 401/403 posterior debe invalidar la sesión.

El backend también expone POST /api/v1/auth/switch-tenant para cambiar el desarrollo activo.

Todo dato local relevante se aísla mediante LocalScope:

- userId del usuario autenticado.
- developmentId del desarrollo activo.

Nunca se deben mezclar cachés, catálogos, operaciones pendientes o avisos entre usuarios o
desarrollos. En la lógica de asignaciones, "estoy como agente" corresponde a agente_id y no
a cerrador_id.

- Registra llamadas y puede asociar/importar audio.
- Consulta historial de llamadas, correos y contactos.
- Registra seguimientos, que también pueden generar actividad de agenda.
- Captura y consulta discovery.
- Muestra comentarios, historial, información de llamada y guiones.

7.3 Agenda

- Presenta actividades por día, semana y mes.
- Soporta filtros y rangos de fecha.
- Permite crear, editar, completar, cancelar y eliminar actividades.
- Las actividades se cachean y las mutaciones compatibles entran en la outbox.
- Los recordatorios se programan como notificaciones locales.
- Las fechas de negocio deben pasar por business_clock.dart.

7.4 Perfil y apariencia

- Muestra identidad de la sesión.
- Administra preferencias locales del perfil y recordatorios.
- AppearanceController sincroniza preferencia de tema mediante /api/v1/preferences cuando
  corresponde.
- La aplicación admite tema claro, oscuro y system.

7.5 Notificaciones y asignaciones

- NotificationService administra avisos locales de actividades y asignaciones.
- ProspectAssignmentController consulta periódicamente nuevas asignaciones.
- El polling normal usa un intervalo de 30 segundos.
- Al tocar un aviso se abre el prospecto o la actividad relacionada.
- Los avisos locales tienen retención de 7 días.

7.6 Llamadas y audio

- PhoneCallService abre la llamada mediante la capacidad del dispositivo.
- CallLogService busca información real de la llamada cuando la plataforma lo permite.
- Si no existe una duración real, el modelo puede marcarla como estimada.
- AudioImportService y la API permiten adjuntar audio a un registro de llamada.
- Estas funciones dependen de permisos y capacidades nativas de Android.


8. OFFLINE-FIRST, CACHÉ Y OUTBOX
--------------------------------

SQLite solo se abre de forma productiva en Android. Las pruebas pueden inyectar una factory
FFI. En plataformas no compatibles, databaseOrNull devuelve null y la app puede seguir
trabajando contra la API, pero no dispone del comportamiento offline completo.

Versión actual del esquema local: 4.
Archivo de base: callerapp.db.

Tablas principales:

- cached_prospects: instantánea de prospectos por usuario/desarrollo.
- cached_activities: instantánea de actividades por usuario/desarrollo.
- cache_metadata: fecha de actualización por ámbito y recurso.
- activity_notifications: avisos persistidos y estado leído/descartado.
- app_metadata: catálogos, discovery, precargas, mantenimiento y mapas de ids.
- pending_operations: outbox de escrituras pendientes.

La outbox usa los estados:

- pending: esperando sincronización o reintento.
- syncing: envío en curso.
- conflict: requiere decisión explícita del usuario.

Operaciones reconocidas por la interfaz:

- agenda.create, agenda.update, agenda.complete, agenda.cancel y agenda.delete.
- prospect.create, prospect.update, prospect.follow_up y prospect.discovery.

Reglas centrales:

- Las creaciones offline usan ids temporales negativos.
- Al recibir el id real del servidor se actualiza la caché y también los payloads de las
  operaciones dependientes.
- Cada operación conserva una Idempotency-Key estable, incluso durante reintentos.
- La falta de conexión no consume el presupuesto de reintentos.
- Los fallos de servidor consumen intentos; después de 5 la operación queda como conflicto.
- Los conflictos no se reintentan automáticamente: el usuario elige reintentar o descartar.
- La sincronización automática se intenta cada 90 segundos solo mientras hay pendientes.
- También se intenta al volver la app a primer plano y mediante "Sincronizar ahora".
- Después de una sincronización real se refrescan Inicio, Prospectos y Agenda.

Mantenimiento:

- Se evalúa aproximadamente cada 24 horas.
- La caché de un ámbito vence a los 30 días según su recurso más reciente.
- Al purgar un ámbito vencido se eliminan cachés, avisos, metadata y claves asociadas de
  app_metadata.
- Cerrar sesión o dejar expirar la sesión no borra inmediatamente la caché.
- Las notificaciones locales tienen retención de 7 días.


9. CATÁLOGOS OFFLINE
--------------------

CatalogCache persiste JSON dentro de app_metadata con claves aisladas por usuario y
desarrollo. Incluye canales, estatus de prospecto, desarrollos, campañas y lotes. Los lotes
también se identifican por desarrollo.

El patrón es remoto primero y fallback por catálogo. El repositorio decide entre remoto y
caché; la UI nunca debe leer CatalogCache directamente. La precarga tiene un intervalo de
12 horas.

Para altas/ediciones offline se necesitan catálogos descargados previamente. Si faltan datos
imprescindibles, como canales u orígenes, Guardar debe quedar deshabilitado o mostrarse un
error claro. No se debe inventar un id. MySQL sigue siendo la fuente de verdad.


10. API REST DEL BACKEND
------------------------

Prefijo principal: /api/v1
Autorización: Authorization: Bearer <JWT> en rutas protegidas.
Mutaciones compatibles: cabecera Idempotency-Key.
Formato habitual: envelope JSON con success/data/message o status según el módulo.

Montajes:

- /api/v1/auth
- /api/v1/leads
- /api/v1/agents
- /api/v1/catalogs
- /api/v1/activities
- /api/v1/preferences
- /api-docs y /api-docs.json para Swagger.
- /static/avatars para avatares.
- /static/call-audio para audio cargado.

Endpoints relevantes:

Autenticación:
- POST /api/v1/auth/login
- POST /api/v1/auth/switch-tenant

Prospectos/leads:
- GET /api/v1/leads
- POST /api/v1/leads
- PUT /api/v1/leads/:id
- POST /api/v1/leads/:id/calls
- GET /api/v1/leads/:id/calls
- POST /api/v1/leads/calls/:id/audio
- POST /api/v1/leads/:id/follow-ups
- GET /api/v1/leads/:id/contact-history
- GET /api/v1/leads/:id/discovery
- POST /api/v1/leads/:id/discovery
- GET /api/v1/leads/:id/emails
- POST /api/v1/leads/:id/emails

Agenda:
- GET /api/v1/activities
- POST /api/v1/activities
- PUT /api/v1/activities/:id
- PATCH /api/v1/activities/:id/status
- DELETE /api/v1/activities/:id

Agentes:
- GET /api/v1/agents
- GET /api/v1/agents/closers

Catálogos:
- GET /api/v1/catalogs/estatus-prospecto
- GET /api/v1/catalogs/canales
- GET /api/v1/catalogs/desarrollos
- GET /api/v1/catalogs/campanias
- GET /api/v1/catalogs/lotes?desarrollo_id=...

Preferencias:
- GET /api/v1/preferences
- PUT /api/v1/preferences

El backend usa consultas parametrizadas y un middleware central de errores. La sesión JWT
expira por defecto en 8 horas, configurable mediante JWT_EXPIRES_IN. El middleware de
idempotencia conserva resultados exitosos y libera la reserva frente a respuestas de error
para permitir una corrección/reintento posterior.

13. CONVENCIONES DE CÓDIGO
--------------------------

- Un archivo por concepto, nombres snake_case y ubicación en la capa correcta.

- Pantallas: composición y coordinación, no lógica de negocio extensa.

- Validadores: funciones puras reutilizables.
- ChangeNotifier para estado compartido existente.
- Inyectar http.Client y dependencias para facilitar pruebas.
- Liberar controllers, focus nodes, listeners y timers en dispose.
- Verificar mounted después de operaciones asíncronas antes de setState/navegar.
- Evitar dobles envíos con flags de operación.
- Usar go_router exclusivamente para rutas principales.
- Usar business_clock.dart; no introducir DateTime.now() en lógica nueva.
- Errores mediante una excepción por dominio y mensajes claros en español.
- No mostrar al usuario detalles crudos del backend.
- Consultas MySQL parametrizadas y errores procesados por middleware central.
- No agregar dependencias, capas o patrones nuevos sin una necesidad concreta.


14. RELOJ Y FECHAS
------------------

El reloj de negocio se centraliza en lib/services/business_clock.dart. El offset de negocio
actual es UTC-5, correspondiente al contexto America/Cancun. La lógica nueva no debe llamar
directamente DateTime.now(); debe usar businessNow u otras utilidades centrales.

Los rangos de fecha inclusivos deben modelarse con inicio del primer día y límite exclusivo
del día posterior al último. Semana comienza en lunes. Se deben considerar meses, años
bisiestos, cambios de mes/año y días sin actividades.
